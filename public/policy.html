1. วัตถุประสงค์และขอบเขต

WAVE ใช้บันทึกหลักฐานที่ตรวจสอบย้อนกลับได้สำหรับการพัฒนา การเชื่อมต่อ Provider การทำงานของ Agent และการเปลี่ยนแปลง Runtime นโยบายนี้มีผลกับข้อความใน Dashboard, Chat, Command, Agent panels, logs, reports, policy pages, pull requests และ handoff ระหว่างผู้ปฏิบัติงานหรือ Agent

หลักการที่ต้องรักษา

  1. Evidence before claims: ทุกคำกล่าวว่า PASS, DONE, CONNECTED หรือ LIVE ต้องมีหลักฐานที่รองรับขอบเขตนั้น
  2. Bounded claims: ผลทดสอบยืนยันได้เฉพาะสิ่งที่ทดสอบจริง ห้ามขยายผลไปยัง Provider, Environment หรือ Execution path อื่น
  3. Staging first: ทดสอบใน Staging ก่อน Production เสมอ การเปลี่ยน Production, Candy website, สิทธิ์, Secret หรือข้อมูลจริงต้องมี Owner approval แยกต่างหาก
  4. Least privilege: การอ่านข้อมูลไม่เท่ากับสิทธิ์เขียน การมี Token หรือการเชื่อมต่อไม่เท่ากับสิทธิ์รันคำสั่ง
  5. Append-only history: หลักฐานเก่าที่เคย PENDING, BLOCKED หรือ FAIL ต้องเก็บเป็นประวัติ ไม่ลบทิ้งเพื่อทำให้รายงานดูเขียว
  6. No secret mirroring: ห้ามนำค่าลับไปคัดลอกไว้ในเอกสาร Policy, GitHub source, D1 evidence JSON, PDF หรือ log

หน้านี้เป็น Public Policy Summary เท่านั้น บันทึกหลักฐานฉบับเต็ม รายละเอียดการตรวจสอบ และข้อมูลภายในที่ไม่จำเป็นต่อการเปิดเผยสาธารณะให้คงอยู่ในพื้นที่ควบคุมสิทธิ์ของ Owner

2. ความหมายของสัญลักษณ์และสถานะ

ระบบต้องใช้คำสถานะตามความหมายต่อไปนี้อย่างสม่ำเสมอ ห้ามตีความตามความรู้สึกหรือความสะดวกในการรายงาน

ค่าความหมายที่ถูกต้องสิ่งที่ห้ามสรุป
-ข้อมูลซ้ำ (duplicate marker) ค่าหลักมีอยู่แล้วใน Master field ก่อนหน้า ไม่ใช่ค่าว่าง ไม่ใช่ข้อมูลหาย และไม่ใช่ข้อมูลใหม่ ต้องอ้างค่าหลักเดิมโดยไม่สร้างรายการซ้ำหรือนับซ้ำห้ามตีความว่า missing, null, failed หรือเป็นหลักฐานอีกชิ้นหนึ่ง หากค่าที่ควรซ้ำไม่ตรงกัน ให้แจ้ง conflict แทนการใช้เครื่องหมายนี้
PASSผ่านการทดสอบที่ระบุ พร้อมหลักฐานและขอบเขตชัดเจนห้ามอ้างว่า Provider ทั้งหมด, Runtime ทั้งหมด หรือ E2E ทั้งระบบผ่าน หากทดสอบเพียงบางขั้น
NOT VERIFIEDยังไม่มีหลักฐานเพียงพอที่จะยืนยันผลห้ามยกระดับเป็น PASS, DONE, LIVE หรือเชื่อมต่อสำเร็จ
PARTIALมีหลักฐานบางส่วน แต่ยังไม่ครอบคลุมขอบเขตที่ต้องการห้ามเรียกว่าผ่านครบหรือ Audit complete
NOT DEPLOYEDไม่มีหลักฐานยืนยันว่ารุ่นหรือ Endpoint นั้นถูก Deploy แล้วห้ามอนุมานจาก Source, Commit, Build หรือการมีไฟล์อยู่ใน Repository
PENDINGยังรอขั้นตอน หลักฐาน หรือการอนุมัติที่ระบุห้ามซ่อนหรือเขียนทับสถานะเดิมเพื่อทำให้ภาพรวมดูสำเร็จ
BLOCKEDทำต่อไม่ได้ ต้องระบุ Blocker, สาเหตุ, ผู้รับผิดชอบ และเงื่อนไขปลดล็อกห้ามรายงานเพียงคำว่า blocked โดยไม่บอกวิธีปลดล็อก
ACTIVEสถานะที่มีหลักฐานยืนยัน ณ เวลาตรวจสอบและในขอบเขตที่ระบุห้ามตีความว่าไม่มีวันหมดอายุ ไม่มีวันถูกเพิกถอน หรือยัง Active อยู่ในเวลาปัจจุบันโดยไม่ตรวจใหม่
ACCEPTEDระบบปลายทางรับคำขอหรือบันทึก Event แล้วห้ามเทียบเท่ากับ RUNNING, SUCCEEDED หรือ EXECUTION COMPLETED
EXECUTION COMPLETEDมีหลักฐานผลลัพธ์สุดท้ายจากการทำงานจริง พร้อม Run ID หรือ Result receipt ที่สัมพันธ์กับคำขอห้ามอ้างจาก HTTP 200/202, Health check หรือข้อความตอบรับเพียงอย่างเดียว
กฎของเครื่องหมายขีด: - คือข้อมูลซ้ำตามที่ Owner ระบุไว้ใน Master record ส่วนสิ่งที่ยังพิสูจน์ไม่ได้ต้องใช้สถานะอย่าง NOT VERIFIED, PARTIAL หรือ NOT DEPLOYED อย่างชัดเจน ห้ามใช้ขีดแทนสถานะที่ยังไม่ทราบ

3. ระดับหลักฐาน: Source ≠ CI ≠ Runtime ≠ E2E

ผลการตรวจแต่ละระดับเป็นคนละข้อเท็จจริง การผ่านระดับหนึ่งไม่ทำให้ระดับถัดไปผ่านโดยอัตโนมัติ

ระดับหลักฐานขั้นต่ำข้อความที่อนุญาตสิ่งที่ยังไม่พิสูจน์
SourceRepository, path, commit SHA, diff และ review ที่เกี่ยวข้อง“Source implementation exists” หรือ “Source review PASS”ยังไม่ยืนยันว่า Build ผ่าน, Deploy แล้ว หรือ Runtime ใช้งานได้
CI / BuildRun ID, commit SHA, job/step, exit result และ test output“CI PASS for the listed workflow steps”ไม่ยืนยันว่ารุ่นถูก Deploy, Secret ถูก Bind หรือ External API ทำงานจริง
Runtimeตรวจ Endpoint/Worker รุ่นที่กำลังให้บริการจริง พร้อมเวลา, response, environment และ version/SHA ถ้าระบุได้“Runtime check PASS at [time] for [endpoint/scope]”Health check ไม่ได้พิสูจน์ว่าคำสั่งธุรกิจหรือทุก Provider ทำงานได้
External End-to-EndCorrelation/Delivery ID, request, target receipt, Run ID และ final result ที่สัมพันธ์กัน“E2E PASS for [specific path]”ไม่ครอบคลุม Provider, payload, permission หรือเส้นทางอื่นที่ไม่ได้ทดสอบ
AuthorizationOwner identity/session, approved plan/capability, scope, expiry/revocation และ audit receipt“Authorized for this specific action and scope”ไม่สร้างสิทธิ์ถาวรหรือสิทธิ์ทั่วทั้งระบบ
D1 integrityRecord ID เดิม, exact serialized JSON, readback และคำนวณ SHA-256 ซ้ำจากข้อมูลที่อ่านกลับมา“GitHub canonical JSON ↔ D1 byte/hash match at the recorded run”ไม่พิสูจน์ว่า Infisical มี JSON สำเนาเดียวกัน หรือว่า D1 ยังตรงกันในเวลาปัจจุบัน
ห้ามใช้ CI PASS เพื่ออ้าง Runtime PASS และห้ามใช้ Source PASS เพื่ออ้างว่า Endpoint ทำงานจริง การตรวจ Health/Readiness เป็นเพียงหลักฐานของ Health/Readiness เท่านั้น

4. กติกาการรายงานผลและ Traffic Light

GREEN · PASS

ใช้ได้เมื่อมีหลักฐานตรงกับขอบเขตที่กล่าวอ้าง ต้องแสดง Run ID, SHA, test result หรือ Runtime evidence ตามประเภทงาน และระบุเวลาที่ตรวจ

BLUE · IN PROCESS

ใช้เมื่องานยังดำเนินอยู่ ต้องระบุขั้นตอนล่าสุด ผู้รับผิดชอบ และขั้นตอนถัดไป ไม่ใช้คำว่า DONE ก่อนมีหลักฐานปิดงาน

RED · BLOCKED

ใช้เมื่องานติดขัด ต้องระบุ Blocker, สาเหตุ, ผู้รับผิดชอบ และเงื่อนไขปลดล็อกที่ตรวจสอบได้

รูปแบบรายงานที่ต้องมี

  • RESULT: ผลที่เกิดขึ้นจริง ไม่ใช่สิ่งที่คาดว่าจะเกิด
  • STATUS: GREEN / BLUE / RED พร้อมสถานะเฉพาะ เช่น NOT VERIFIED หรือ PARTIAL
  • SCOPE: Environment, endpoint, provider, action และขอบเขตที่ทดสอบ
  • EVIDENCE: Commit SHA, Run ID, test output, timestamp, response หรือ receipt ที่เกี่ยวข้อง
  • LIMITATION: สิ่งที่ผลทดสอบนี้ยังไม่พิสูจน์
  • NEXT: ขั้นตอนถัดไป ผู้รับผิดชอบ และเงื่อนไขที่จะยกระดับสถานะ

หากหลักฐานขัดแย้งกัน ให้เก็บหลักฐานทั้งสองชุด ระบุเวลาและขอบเขตของแต่ละชุด และเปิดประเด็นตรวจสอบ ห้ามเลือกเฉพาะหลักฐานที่ทำให้สถานะเป็นสีเขียว

6. ความปลอดภัยของ Credential, Secret และ Evidence

การแยกหน้าที่ของระบบจัดเก็บ

  • GitHub: Source code, canonical evidence JSON, version history และ CI receipts
  • Cloudflare D1: Operational evidence JSON, metadata และ digest ที่ใช้ตรวจ integrity ตามขอบเขตที่กำหนด
  • Infisical / approved secret store: Secret values, machine identity และ certificate lifecycle material ภายใต้ scope ที่อนุญาต
  • 1LSS / owner-main: ตัวอ้างอิง Session continuity ไม่ใช่สำเนา Vault และไม่ใช่การมอบสิทธิ์
  • ห้ามบันทึก Password, API token, Bearer token, OAuth code, Cookie, PEM, Private key หรือค่าลับอื่นลงใน Policy page, Source, D1 evidence JSON, PDF, Issue comment หรือ log
  • ห้ามนำค่า Secret จาก Infisical ไป mirror ใน D1 เพื่อทำให้ดูเหมือนข้อมูลตรงกันแบบ 1:1 การตรวจ JSON hash ระหว่าง GitHub กับ D1 ไม่ใช่หลักฐานว่า Infisical มี JSON เหมือนกัน
  • Log และ UI ต้องแสดงเฉพาะสถานะ จำนวน Resource ID ที่จำเป็น ข้อผิดพลาดที่ลบข้อมูลลับแล้ว และ Evidence reference ที่ได้รับอนุญาต
  • การยืนยันตัวตนผ่าน OIDC หรือการอ่าน Secret สำเร็จ ไม่ได้พิสูจน์ว่า Credential ทุกตัวมี scope ถูกต้องหรือใช้งานกับทุก Provider ได้
  • Certificate ที่มีวันหมดอายุและการตั้ง Auto-renew ต้องตรวจทั้งสถานะปัจจุบัน วันหมดอายุ และหลักฐานการต่ออายุจริง ห้ามเรียกการตั้งค่า renewal ว่าต่ออายุสำเร็จแล้ว
  • ผล mTLS ที่ผ่านบน localhost หรือ test environment ไม่ได้ยืนยันว่า External WAVE endpoint ใช้ mTLS สำเร็จ
Public disclosure: หน้า Policy นี้ไม่เปิดเผย Secret, Private key, token, internal database identifier, credential path หรือรายละเอียดการเข้าถึงที่ไม่จำเป็น หลักฐานฉบับเต็มยังอยู่ในพื้นที่ควบคุมสิทธิ์ของ Owner

7. Owner approval, Yellow Stone และการเปลี่ยนแปลงระบบ

สิทธิ์ในการอ่านหรือเรียก API ไม่ใช่สิทธิ์อนุมัติให้เกิดผลข้างเคียง ทุกคำสั่งที่เปลี่ยนสถานะหรือทรัพยากรต้องผ่าน Authorization Gate ที่กำหนดสำหรับการกระทำนั้น

การกระทำกติกา
Read-only inspectionใช้สิทธิ์ต่ำสุดและจำกัดขอบเขต แสดงผลเฉพาะข้อมูลที่จำเป็น
Write / execute / deployต้องมีแผนงานที่ระบุ Scope และ Owner approval ตามนโยบายก่อนเริ่ม
Production / Candy websiteห้ามเปลี่ยนแปลงโดยอาศัย Certificate lincenc นี้เพียงอย่างเดียว ต้องได้รับการอนุมัติโดยตรงแยกต่างหาก
D1 schema หรือข้อมูลปฏิบัติการการมีบันทึก Certificate ไม่ใช่การอนุมัติให้เปลี่ยน Schema หรือข้อมูล D1 อื่น
Runner / Terminalห้ามสร้าง Runner service เพิ่มหรือข้าม Terminal/Yellow Stone gate โดยอนุมานจากสถานะที่เชื่อมต่อแล้ว
Provider write permissionsRead API ที่ผ่านแล้วไม่อนุญาตให้เขียน ส่งข้อความ แก้ไขข้อมูล หรือเรียกเก็บเงินโดยอัตโนมัติ
Revocation / expiryสิทธิ์ต้องจำกัดตามเวลา Scope และกลไกเพิกถอน การระบุ “permanent” ในบันทึกไม่สามารถลบข้อจำกัดของใบรับรองที่หมดอายุได้

ณ Snapshot ที่สรุปไว้ signed_capability_grant = false จึงห้ามถือว่ามีการมอบสิทธิ์รันคำสั่งแบบลงลายมือชื่อแล้ว การผ่าน READ หรือ Approval challenge ไม่ได้แปลว่ามี Owner-confirmed execution result

8. ความสดใหม่ของหลักฐานและการหมดอายุ

  • ทุก Evidence ต้องระบุเวลาที่เก็บและ Environment ที่ตรวจ
  • สถานะจาก Snapshot วันที่ 19 ตุลาคม 2026 เป็นสถานะ ณ ขอบเขตของหลักฐานที่อ้างถึง ไม่ใช่การยืนยันสถานะปัจจุบันแบบ Real-time
  • ก่อนอ้างว่า Runtime ยังพร้อมใช้งาน ให้ตรวจ Endpoint จริงและระบุเวลาที่ตรวจใหม่
  • ก่อนอ้างว่า Certificate/Leaf ยัง Active ให้ตรวจ Trust chain, Subject, expiry และ revocation/renewal state ที่เกี่ยวข้อง
  • ก่อนอ้างว่า D1 ยังตรงกับ GitHub ให้ทำ Readback ใหม่และคำนวณ digest จากข้อมูลที่อ่านกลับมา ไม่ใช้ Hash เก่าแทนการตรวจล่าสุด
  • เมื่อมี Commit ใหม่ ผล CI เก่าใช้ยืนยันได้เฉพาะ SHA ที่รันจริง ห้ามนำผลของ SHA หนึ่งไปอ้างแทนอีก SHA หนึ่งโดยไม่ตรวจความสัมพันธ์
  • เมื่อมีการเปลี่ยน Endpoint, Secret binding, permission, provider version หรือ execution adapter ต้องทำการทดสอบที่ได้รับผลกระทบซ้ำ

10. การตรวจทาน การแก้ไข และการจัดการความขัดแย้ง

  1. เมื่อแก้ไข Source หรือ Policy ให้สร้าง Version/Commit ใหม่ และเก็บประวัติเดิมไว้
  2. เมื่อมีหลักฐานใหม่ ให้เพิ่ม Event หรืออัปเดตสถานะเฉพาะ Scope ที่หลักฐานใหม่ครอบคลุม ห้ามลบข้อจำกัดทางประวัติศาสตร์
  3. เมื่อหลักฐานจาก Source, CI, Runtime และ External endpoint ไม่ตรงกัน ให้รายงานแยกตามระดับ ไม่ใช้ระดับหนึ่งกลบอีกระดับ
  4. เมื่อค่าในฟิลด์ที่ทำเครื่องหมาย - ไม่ตรงกับ Master value ให้เปลี่ยนเป็นประเด็น Conflict และตรวจต้นทาง ห้ามบังคับนับเป็น Duplicate
  5. การเปลี่ยน Policy ที่ส่งผลต่อ Production, credential, permissions, D1 schema หรือ execution authority ต้องผ่าน Owner approval ก่อนดำเนินการ
  6. การปิดงานต้องระบุหลักฐานสุดท้ายและข้อจำกัดที่เหลือ หากมีขั้นตอนสำคัญที่ยัง NOT VERIFIED ให้คงสถานะนั้นไว้

เกณฑ์ขั้นต่ำก่อนใช้คำว่า DONE

  • มี Requirement และ Scope ที่ชัดเจน
  • มี Source SHA และผล CI ที่สัมพันธ์กับ SHA นั้น หากงานมีการเปลี่ยนโค้ด
  • มี Runtime proof เมื่อกล่าวอ้างว่า Deploy หรือใช้งานจริง
  • มี End-to-End receipt และ final result เมื่อกล่าวอ้างว่าการสื่อสารหรือคำสั่งทำงานถึงปลายทาง
  • มี Owner approval เมื่อมี side effect ที่ต้องอนุมัติ
  • ระบุข้อจำกัดที่เหลืออย่างตรงไปตรงมา ไม่มีการใช้ - ซ่อนสถานะที่ยังไม่พิสูจน์

11. ข้อจำกัดและคำชี้แจง

นโยบายนี้เป็นแนวทางการควบคุมการทำงานและการรายงานหลักฐานของ WAVE / OGENIC ไม่ใช่คำรับประกันความพร้อมใช้งานอย่างต่อเนื่อง ไม่ใช่การรับรองความปลอดภัยจากผู้ตรวจสอบอิสระ ไม่ใช่ใบรับรองจากหน่วยงานกำกับดูแล และไม่รับประกันว่าบริการของบุคคลที่สามจะพร้อมใช้งาน
